# Independent task runs (downstream extension)

Date: 2026-11-16. This fork's user requested phase 1 of the pstack integration after the isolated public-API feasibility study. Implementation starts from upstream dev `218a6bd`; DSH execution tests stay pinned to `0.2.2-rc.1`.

## Scope and existing decisions

A task run is an execution instance, separate from a persistent Bot, a chat thread, the group task board and a group goal. The existing Bot-to-Bot handoff and group task contracts keep their behavior. Native delegation remains blocked in Bot chats. The new `start_task`, `list_task_runs`, `read_task_run`, `steer_task` and `cancel_task` tools provide the explicit run-aware path. Setting plugin configuration `taskRuns: false` disables this extension.

This is an explicit downstream extension of the exclusions in `2026-10-10-bot-runtime.md` and `2026-10-16-bot-handoffs.md`, authorized for this fork by its user; it does not claim upstream maintainer approval. It introduces no engineering roles, playbook state machine, fixed retry count, budget policy, acceptance signature or group-goal success condition. pstack's engineering text is unchanged in phase 1.

## Execution and identity

The plugin owns a stable root Agent as the host of each top-level run and uses the public subagent `spawn` provider with caller delivery. The host makes no model calls. Its identity is independent of the Bot chat part. Workers have their own reserved Session identity, explicit instructions and brief; the Agent's awaited creation hook applies per-run policy and task tools before its first model request. Nested tasks use their live parent worker as their native parent and native `delivery: 'parent'`; only top-level runs use caller delivery and the Bot-part bridge. Native completion notices wake the coordinator before its final output is captured, so a dispatch acknowledgement does not become the final result. Unsupported project-root changes fail explicitly instead of flattening the tree.

Persist `id`, `ownerBotId`, optional `roomId`/`parentRunId`, the originating chat Session, native host/worker/run identities, requested and actual model/effort, current directory, original project root, sandbox/approval policy, timestamps, output reference and notification state. A task Session never enters `chatOwners`, `groupOwners` or `state.agents`. Ownership by a Main Bot does not make a worker a Main Bot.

Tool callers may inspect/control their own runs. A worker may inspect itself and its descendants and control only descendants; it cannot use its owner's Bot identity to control unrelated work or team management. User endpoints may inspect/control all runs. An explicit task directory must exist, pass the existing DS-Bot data-directory guard (including its managed team-workspace exception), and not widen a confined caller's project root. A task may narrow but not widen its caller's sandbox mode. Model selection uses the actual calling Agent when no model is supplied and never updates the profile default or persistent Bot configuration. Unsupported requested models/efforts return facts to the caller rather than silently choosing another route.

## Completion and continuation

Admission is not completion. Persist `admission: pending | accepted | rejected` separately from execution status. Rejected admission retains its reason and informs the original tool caller without fabricating a native result or a second completion notification. Keep production execution outcomes distinct: completed, failed, cancelled and unknown. Output-limit settlement is not successful completion. Starting a later fresh task creates a new run; steering a live run does not restart a terminal run. Explicit terminal-session resume/fork is not advertised until its attempt and restoration contract is tested.

Keep full results before marking their reference durable. Show the retained preview in the roster and fetch the full result on expansion; paginate real Session logs. Long Bot notifications reuse DS-Bot's attachment path, and failures reuse its existing credential-safe error normalization. Completion is addressed by run identity to the calling run or the current part of the originating Bot thread/group Session. Starting another independent chat thread must not steal a background thread's result. A removed group or thread leaves a visible undeliverable result, rather than rerouting private work to another conversation. Existing handoff work, when present, tracks this run as an explicit child until its result is consumed.

A notification has its own durable message identity and delivery state. Duplicate settlements do not create another result. On reload, reconcile known terminal results and notification identities through public Session history. An interrupted or unreadable execution becomes unknown; do not auto-replay the brief or imply exactly-once file/network effects. Runtime disposal explicitly stops/drains owned execution handles; it does not stop the Bot's other chats. Queue interrupted-state writes before the first asynchronous drain so the store's shutdown barrier durably saves them. Deleting a Bot stops that owner's task tree, blocks further admission and suppresses result wake-ups to the deleted conversation, while other owners continue.

Private-Bot task execution is not enabled until task-result persistence integrates with private archives. Native model routes are supported; the separate local CLI-agent backends are not exposed through TaskRun. These limits do not unlock native delegation or reduce a requested candidate count.

## User surface

Expose task runs in the Bot details and, when applicable, the matching group's overview. Show distinct instances, owner/parent, actual model, directory, status, result/error and delivery state. Running entries allow a directed instruction and Stop; history exposes real Session events. The group task board remains the member's explicit work summary and is not the execution engine.

## Acceptance

Use the actual DS-Bot runtime and production AgentLoop with a scripted adapter in isolated data. Cover first-step initialization and setup rejection; fresh markers with DS-Bot memory/hooks mounted; different simultaneous routes/efforts/directories/modes; repeated-model instances; nested children and independent completion; real Bot part switching while a task runs; exact cancellation preserving siblings; Main/worker authorization; duplicate/late settlement; and reload with durable result or explicit unknown. Separately test the interactive client and an isolated full-host smoke. Run the repository's full unit tests, lint and generated-client checks. Preserve recorded failures and disclose untested shell/process or model behavior. This is execution-layer acceptance, not pstack workflow or overnight autonomy acceptance.
